# LinguaFlow PM 方法论 & 团队管理手册
> 版本 1.0 · 2026-08-04 · 适用于 1–2 人前端小团队 / 独立开发
> 设计原则：轻量、低仪式感、显式化、可交接。反对形式主义与范围蔓延。

## 0. 为什么需要它（痛点对齐）
你最大的痛是「需求 / 规格不清」。后果：开发靠估、做完才发现理解错、知识锁在脑子里、想加人接不上。
本手册把"脑子里的事"变成"文件里的事"。

## 1. 核心循环（每周都在转）
```
想法 → 规格 → 任务 → 构建 → 验收 → 复盘
Idea → Spec → Tasks → Build → QA → Reflect
```
- 任何大于 1 小时的活，先有 Spec 再动手。
- 任何 Spec 改动，先更新 site-setup.md，再改任务。
- 每周五 30 分钟 solo 复盘（见 §6）。

## 2. 规格模板（复制即用）
存为 `ai/memory-bank/site-setup.md`（本项目已建）。新项目 / 新大特性新建一份。
包含：定位一句话 / 当前状态(事实) / 产品原则(约束) / 范围边界 / 目标用户 / 成功指标 / 待立项候选(提案,非需求) / 技术栈速查。
⚠️ 铁律：提案 ≠ 需求。候选区项未批准前不进任务库。

## 3. 任务拆解规则
- 单任务 30–60 分钟可交付。
- 每条含：描述 + 可测验收标准 + 涉及文件 + 引用规格章节。
- 验收必须可测（"页面无报错并含 X 区块"而非"做好导航"）。
- 不写"豪华 / 高级"类要求，除非规格明写。基础实现即合格。
- 首版普遍需要 2–3 轮修订——别追求一次完美。

## 4. Memory Bank 约定（知识不随人走）
```
ai/memory-bank/
  site-setup.md        # 唯一事实来源（规格/现状）
  tasks/<slug>-tasklist.md  # 任务清单
  PM-METHODOLOGY.md    # 本手册
  README.md            # 索引 / 如何使用
```
（项目级日记与长期笔记另有 `.workbuddy/memory/`，按日追加。）

## 5. 质量门（每个任务 merge 前自查）
- [ ] `npm run build` 无 TS / 构建错误。
- [ ] 移动端响应式正常。
- [ ] 关键页面有 Playwright 截图（`qa-playwright-capture.sh`）。
- [ ] 命令不挂后台、不自带起服务。
- [ ] 图片源合规（picsum / Unsplash，禁 Pexels）。
- [ ] 表单 / 交互可用（若有）。

## 6. 独立 / Solo 周节奏（30 分钟 / 周）
周五 30 分钟：
1. 看任务库：哪些 done / 卡住 / 该删。
2. 看 site-setup：有没有新想法要进候选区。
3. 写一句本周复盘到 memory 日记。
即使一个人也要有节奏，否则"小"会变成"乱"。

## 7. 团队管理（1–2 人场景）
1–2 人不是"不用管"，而是"靠机制代替会议"。
- **Ownership**：即使 solo，每个任务也写清"负责人 = 自己"；一旦加人，直接能分。
- **异步交接文档**：任何"只有你知道"的事，写成 1 段话进 memory / 规格。新人 / 外包第一天能靠文档上手。
- **决策日志**：重大取舍（如"暂不做后端"）写进 site-setup 原则区，避免反复争论。
- **何时扩人**：当同一周有 ≥3 个任务因"没人手"停滞，或你连续 2 周复盘都在说同一阻塞 → 该找人了。
- **沟通节奏**：1–2 人用每日 5 分钟异步站会（文字：昨天 / 今天 / 阻塞）即可，不必拉会。
- **外部协作**（设计 / 外包）：给对方的永远是"规格 + 验收标准"两份文件，不是口头描述。

## 8. 反模式（踩过的坑）
- 范围蔓延：做着做着加戏 → 任何新增先回规格，批准才做。
- 规格不清就开干 → 先写一句话定位 + 验收，再写代码。
- 豪华病：没说要动画 / 高级视觉却自作主张 → 基础实现优先。
- 知识锁脑：改完不记 → 每次实质改动补 memory 日记。
- 一次性完美幻想 → 接受 2–3 轮修订。

## 9. 工具建议（轻量，勿上 Jira）
- 规格 / 任务 / 方法论：本 memory-bank 的 Markdown（git 版本化）。
- 看板：任务清单里的 `[ ]` 勾选即可；需要可视化再用 GitHub Projects / 看板。
- 周复盘：memory 日记 3 行。
